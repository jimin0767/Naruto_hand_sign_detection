# 웹캠 화면 설계 — 게임 화면 좌우 하단에 두 플레이어

**작성일** 2026-08-21 · **상태** 확정

유니티 게임 화면 **왼쪽 하단에 내 웹캠, 오른쪽 하단에 상대 웹캠**을 띄운다.
크기는 상대가 맺는 수인을 눈으로 읽을 수 있는 정도.

관련 문서: [2026-08-20-battle-system-design.md](2026-08-20-battle-system-design.md) (대전 규칙 · D장 코드 구조)

---

## 1. 밸런스에 미치는 영향 — 검토 결과 안전

상대가 수인을 맺는 것이 보이면 시전이 끝나기 전에 회피를 시작할 수 있다.
설계서 §4.3 이 "발사를 보고 나서 움직여라"를 지속시간으로 강제하고 있으므로,
이것이 무력화되는지 확인했다.

공격자는 발사 **2.5초(3사인) / 3.5초(4사인) 전**부터 사인을 맺기 시작한다.
방어자가 그것을 보고 즉시 회피를 시작한 경우(발사 시각 = 0 기준):

| 회피기 | 지속 | 유효 시작 구간 | 상대 사인 시작과 동시에 걸면 |
|---|---|---|---|
| 변신술 | 5.0s | −1.5s ~ +3.5s | ❌ 실패 |
| 분신술 | 6.0s | −2.5s ~ +3.5s | ❌ 실패 (경계 만료) |
| 진공파 | — | −3.5s ~ +2.5s | ⚠️ 3사인 상대에게만 성립 |

**결론: 규칙을 바꿀 필요가 없다.** 모든 회피 지속시간이 비행시간 6.0초보다 짧아,
일찍 걸면 일찍 꺼진다. 상대 화면을 봐도 "빨리 거는" 이득이 없다.

실제로 얻는 것은 타이밍이 아니라 **정보**다 — 어떤 기술이 오는지 알고 §4.1 의
가위바위보(맨몸↔치도리 / 분신↔물총)에서 맞는 카운터를 고르는 것.
수인 순서를 외운 쪽이 유리해지므로 프로젝트 주제와도 맞는다.

## 2. 구조

```
PC-A                                            PC-B
┌──────────────┐                                ┌──────────────┐
│ 08_bridge.py │                                │ 08_bridge.py │
│  프레임 1장  │                                │              │
│  ├─ YOLO ────┼──► 5010 시전                   │              │
│  └─ JPEG ────┼──► 5012 영상 (로컬만)          │              │
└──────────────┘                                └──────────────┘
        │ 127.0.0.1                                     │
┌───────▼──────┐                                ┌───────▼──────┐
│ Unity A      │  ─────── 5013 영상 중계 ──────►│ Unity B      │
│ 좌하 = 내것  │◄────── 5013 영상 중계 ─────────│ 좌하 = 내것  │
│ 우하 = 상대  │                                │ 우하 = 상대  │
└──────────────┘                                └──────────────┘
```

### 왜 파이썬이 상대에게 직접 안 보내는가

파이썬은 `127.0.0.1` 밖으로 나가지 않는다. 상대 주소를 아는 것은 유니티뿐이다
(`UnityTransport.GetEndpoint(clientId)`).

- **호스트는 클라이언트가 접속하기 전까지 상대 IP 를 모른다.** 결국 유니티가
  알려줘야 하는데, 그러면 파이썬이 대전 상태를 알아야 해서 D.1 의 경계가 무너진다.
- 영상은 **Netcode 를 타지 않는다.** 초당 600KB 를 게임 상태 동기화와
  같은 채널로 흘리면 시전·판정 패킷이 밀린다.

### 왜 포트를 둘로 나누는가

`5012` = 내 파이썬, `5013` = 상대 유니티. **어느 소켓으로 들어왔는지가 곧 신원**이라,
패킷에 "누구 얼굴인지"를 실어 보내고 그것을 신뢰할 필요가 없다.

## 3. 패킷

```
magic "NJVF" (4) | version (1) | slot (1) | frame_id (4) | JPEG 본문...
```

- 10바이트 헤더, 리틀엔디언 (`<4sBBI`)
- `slot` 은 디버깅 표시용이며 판정에 쓰지 않는다 (신원은 포트로 정한다)
- `frame_id` 로 늦게 도착한 프레임을 버린다
- 한 프레임 = UDP 한 개. 64KB 를 넘으면 그 프레임을 버리고 경고를 1회 남긴다

**영상은 시전과 반대로 '최신값 덮어쓰기'다.** 시전은 이산 사건이라 하나를 잃으면
플레이어가 몇 초를 잃지만, 영상은 20fps 중 한 장이라 눈에 보이지 않는다.
그래서 큐가 아니라 마지막 것만 들고 있는다.

## 5. 구현 시 반드시 지킬 것

### 5.1 인식 잠금 중에도 영상은 흘러야 한다

현재 파이썬 루프는 잠기면 `continue` 로 프레임을 통째로 건너뛴다.
그대로 두면 공격을 날린 **6초 동안 내 얼굴이 얼어붙는다.**

캡처 · 인코딩 · 전송을 게이트 검사보다 **앞으로** 옮긴다.
건너뛰는 것은 YOLO 추론뿐이다 — 잠금 동안 GPU 를 쉬게 하는 원래 목적은 그대로 유지된다.

### 5.2 JPEG 디코딩은 메인 스레드에서만

`Texture2D.LoadImage` 는 메인 스레드 전용이다.
수신은 백그라운드 스레드, 디코딩은 `Update()` 에서 최신 한 장만. 480p 기준 1~3ms.

### 5.3 좌우 하단 배치

두 RawImage 를 각각 화면 좌하 · 우하에 앵커한다.
크기·여백은 인스펙터에서 조절 가능하게 한다.

## 6. 실패 처리

| 상황 | 동작 |
|---|---|
| `--fake-cast` (카메라 없음) | 영상 없음. 빈 화면, 에러 아님 |
| 상대 미접속 | 중계 건너뜀 |
| JPEG 가 64KB 초과 | 그 프레임 버리고 경고 1회 (품질을 낮추라고 안내) |
| 포트 이미 사용 중 | 영상만 끄고 게임은 정상 진행 |
| 파이썬이 죽음 | 마지막 프레임이 남아있음. 게임은 그대로 진행 |

| 항목 | 값 | 근거 |
|---|---|---|
| 해상도 | 640×480 | 수인을 읽을 수 있는 하한 |

## 8. 안 하는 것 (YAGNI)

- **프레임 청킹**: 한 프레임이 64KB 에 들어가므로 불필요. 넘으면 품질을 낮추면 된다.
- **코덱(H.264 등)**: LAN 2인 대전에 JPEG 로 충분하다. 인코더 의존성을 늘리지 않는다.
- **오디오**: 요청에 없다.
- **3인 이상**: 대전이 1:1 이므로 화면도 2개로 고정한다.
