# 대전 시스템 설계 — 인술 배틀 (Naruto Hand Sign Detection)

**작성일** 2026-08-20 · **갱신** 2026-08-21 · **상태** Section A/B/C/D 확정, 구현 완료

demo-short.csv의 7가지 인술을 공격 / 회피 / 반격 기술로 규정하고, HP·차크라·투사체
비행·인식 잠금으로 구성된 1:1 실시간 대전 규칙을 정의한다.

---

## 1. 대전 형식

**1:1 네트워크 대전.** 두 대의 PC, 각자 웹캠. 양쪽 모두 자기 화면에서 자기 손 사인을
인식하고, HP·차크라·투사체 상태를 서로 동기화한다. 상대의 시전과 발사를 화면으로 보고
반응하는 것이 게임의 핵심.

## 2. 전역 시스템

| 항목 | 값 |
|---|---|
| HP | 100 (0이 되면 패배) |
| Chakra | 최대 100, 시작 100 |
| Chakra 회복 | **2초마다 +6** (초당 3.0), 기절·잠금 중에도 계속 |
| 투사체 비행 시간 | **6.0초** |
| 시전 시간 | 3사인 ≈ **2.5초**, 4사인 ≈ **3.5초** |
| 차크라 부족 시 | 시퀀스가 매칭돼도 발동 실패, 차크라 소모 없음 |

### 시전 시간의 근거

`handsign/smoothing.py`의 `SignSmoother`는 25프레임 창에서 18표가 모여야 사인을
확정하고(≈0.3초 @78FPS), 다음 사인으로 넘어가려면 손을 내려 창을 비워야 한다. 릴리스
갭까지 합쳐 사인당 0.7~0.9초. 3사인 ≈ 2.5초, 4사인 ≈ 3.5초는 여기서 역산한 값이다.

**사인 개수가 곧 밸런스 축이다.** 3사인은 빠르므로 비싸거나 조건부여야 하고, 4사인은
느린 만큼 안정적이어야 한다.

## 3. 인식 잠금 (Recognition Lock)

> **공격을 발사한 사람은 그 공격이 상대에게 도달할 때까지 사인 인식이 꺼진다.**

- 잠금 대상은 **공격자만.** 방어자는 그 6초 동안 자유롭게 인식된다.
- 잠금 시작은 **발사(시전 완료) 시점.** 시전 중에는 어차피 그 시퀀스를 입력 중이다.
- 잠금 중에는 사인 입력이 쌓이지 않는다 (인식 자체가 꺼짐).
- 차크라 회복은 잠금 중에도 계속된다.
- 방어자가 회피 대신 **공격으로 응수하는 것도 가능**하다. 그러면 방어자도 잠기고,
  날아오던 공격은 그대로 맞는다 — "맞딜" 선택지.

이 규칙 때문에 전투는 실시간 난타전이 아니라 **턴제 교환(exchange)** 구조가 되며,
동시에 존재하는 투사체는 **최대 2개**(양쪽이 하나씩)로 제한된다.

## 4. 기술 7종

### 4.1 공격 3종

| 기술 | 사인 | 시전 | Chakra | 데미지 | 관통 |
|---|---|---|---|---|---|
| ⚡ **Chidori** (Lightning) | 3 | 2.5s | 30 | **22** | 1 |
| 🔥 **Dragon Flame Jutsu** (Fire) | 4 | 3.5s | 28 | 18 | 2 |
| 💧 **Water Bullet Jutsu** (Water) | 4 | 3.5s | 22 | 14 | 3 |

관통 수 = **Clone 상대 명중 확률**(관통/3). 세 기술의 데미지/차크라 효율은 비슷하고,
차이는 오직 **"상대가 Clone 상태냐"** 에서 갈린다.

| 기술 | Clone 상대 명중률 | 기대 데미지 |
|---|---|---|
| ⚡ Chidori | 1/3 | 7.3 (도박) |
| 🔥 Dragon Flame | 2/3 | 12.0 |
| 💧 Water Bullet | 3/3 = **100%** | 14.0 (확정) |

핵심 삼각구도:
- **맨몸 상대** → Chidori (22, 3사인이라 빠름)
- **Clone 깔린 상대** → Water Bullet (확정 14)
- **애매하면** → Dragon Flame (중간)

Chidori는 효율(0.73)이 가장 높지만 관통 1이라 **차크라 18짜리 Clone 한 방에
카운터당한다.** 비싼 강공격 ↔ 싼 카운터의 가위바위보.

### 4.2 공격 + 기절 1종

| 기술 | 사인 | 시전 | Chakra | 데미지 | 관통 | 부가 |
|---|---|---|---|---|---|---|
| 🪨 **Earth Dragon Bullet** (Earth) | 3 | 2.5s | 30 | 10 | 2 | **기절 2.0초** |

기절의 가치는 데미지가 아니라 **회피 시전 차단**이다. 기절 중에는 사인 인식이 차단되고
진행 중이던 시퀀스가 리셋되므로, 상대는 회피기(3사인 2.5초)를 제때 못 맞춘다.
데미지 10짜리 약한 기술이 아니라 **"확정타 만들기"** 기술.

> **튜닝 항목.** 비행 6초가 되면서 상대의 회피 여유가 늘어나 기절 2초의 콤보 가치가
> 다소 희석됐다. 다만 기절 해제 직후 사인 안정화에 또 시간이 걸리는 파이프라인 특성상
> 체감은 2초보다 길다. **실측 후 조정**하되, 지속시간을 늘리기보다
> "기절 중 차크라 회복 정지"를 먼저 붙일 것.

### 4.3 회피 2종

| 기술 | 사인 | 시전 | Chakra | 지속 | 효과 |
|---|---|---|---|---|---|
| 🌀 **Transformation Jutsu** | 3 | 2.5s | 30 | **5.0초** | 도착한 공격 **완전 무효** |
| 👥 **Clone Jutsu** | 3 | 2.5s | 18 | **6.0초** | 본체 포함 3명, 관통 수에 따라 확률 회피 |

**두 기술은 강/약이 아니라 다른 축으로 갈린다:**
Transformation = 비싸다 / 짧다 / 확실하다 · Clone = 싸다 / 길다 / 불확실하다.

#### 선제 패널티는 숫자로 유도된다

별도 규칙 없이, **지속시간을 비행시간(6초)보다 짧게** 잡아 "발사를 눈으로 확인하고
나서 손을 움직여야 한다"를 강제한다.

```
[반응 시전 — 성공]
  0.0s  상대 발사 확인, 시전 시작
  2.5s  회피 ON  ─────────┐
  6.0s  공격 도착  ✅     │  여유 1.5초
  7.5s  회피 OFF ─────────┘

[선제 시전 — 실패]
  0.0s  상대가 시전을 시작하는 걸 보고 같이 시작
  2.5s  회피 ON  ─────────┐   (상대는 이 시점에 발사)
  7.5s  회피 OFF ─────────┘
  8.5s  공격 도착  ✗ 이미 꺼짐
```

Transformation 지속이 4초였다면 여유가 0.5초뿐이라 사실상 도박이 된다. 5초가 하한.

#### Clone 상시 유지 억제

```
Clone           18 / 6.0초 = 초당 3.0  ←→  회복 초당 3.0   ⚖️ 정확히 상쇄
Transformation  30 / 5.0초 = 초당 6.0  ←→  회복 초당 3.0   ✗ 상시 유지 불가
```

Clone은 싸서 상시 유지가 최적해가 될 위험이 있었으나, 지속을 6초로 맞추면 **유지 비용이
회복량 전부와 정확히 같아져 공격을 못 하게 된다.** 규칙 추가 없이 숫자로 억제.

### 4.4 반격 1종

| 기술 | 사인 | 시전 | Chakra | 효과 |
|---|---|---|---|---|
| 🌪️ **Vacuum Wave** (Wind) | 4 | 3.5s | 25 | 날아오는 공격 1개를 **원래 위력 그대로 반사** |

- 4사인 3.5초 vs 비행 6.0초 → **여유 2.5초.** 발사를 보자마자 움직여야 한다.
- 반사된 투사체는 **다시 반사 불가**. 단, **회피로는 피할 수 있다.**
- 날아오는 공격이 없는데 시전하면 **차크라 25만 소모하고 불발** (낚시 리스크).
- Chidori를 반사하면 상대가 22를 맞는다 — 판을 뒤집는 스윙.

**반사 시 잠금 소유권 이전:**

| | 반사 전 | 반사 후 |
|---|---|---|
| 원래 공격자 | 🔒 잠김 | 🔓 **해제** — 방어자가 됨. 회피 가능 / 반격 불가 |
| 반사한 사람 | 🔓 자유 | 🔒 **잠김** — 6초 |

이 이전이 없으면 반사당한 쪽이 인식이 꺼진 채로 자기 기술을 맞아 즉사급 페널티가 된다.

## 5. 판정 규칙

### 5.1 회피 상태의 수명

1. **공격 1개당 회피기 1개만.** 이미 회피 상태면 다른 회피기 시전은 불발(차크라 소모 없음).
   Transformation + Clone 중첩 금지.
2. **판정 1회 후 즉시 종료.** 회피됐든 맞았든, 판정이 끝나면 남은 지속시간과 무관하게
   회피 상태가 사라진다.

### 5.2 도착 시 판정

```
① 회피 상태 = Transformation → 무효화
② 회피 상태 = Clone          → (관통 수 / 3) 확률로 명중, 아니면 무효
③ 회피 상태 없음             → 풀 데미지 (+ Earth Dragon이면 기절 2.0초)
→ 어느 경우든: 회피 상태 소멸, 공격자 잠금 해제
```

### 5.3 그 외

- **기절 중**: 사인 인식 차단, 진행 중 시퀀스 리셋, 이미 발사한 투사체는 정상 비행,
  차크라 회복은 계속.
- **차크라 부족**: 시퀀스가 매칭돼도 발동 실패. 차크라를 소모하지 않고 UI에 표시한 뒤
  시퀀스만 리셋.
- **잠금 중 시퀀스**: 인식이 꺼져 있으므로 입력이 쌓이지 않는다.
- **회피 후 반격**: 회피 시전(2.5초) 완료 후 도착(6.0초)까지 3.5초가 남으므로
  **공격 시전 2.5초를 추가로 넣을 수 있다.** 숙련자의 플레이.
- **동시 사망**: 양쪽 HP가 같은 틱에 0이면 무승부.

## D. 코드 구조 (2026-08-21 확정 · 구현 완료)

### D.1 권한을 어디에 둘 것인가

**전투 규칙은 Unity(C#)에 두고, 파이썬은 순수 센서로 만든다.**

파이썬에 규칙을 두는 안(§7이 원래 가정하던 방향)은 두 PC 사이의 동기화 계층을
새로 만들어야 한다 — 권한, 틱 동기, 재접속까지. 그런데 Unity 쪽에는 익환님이 만든
Netcode 기반 서버 권한 동기화가 이미 돌아가고 있다. 그걸 두고 같은 것을 파이썬으로
다시 짜는 것은 낭비이고, `PVPPlayerSync` · `PVPHudBridge` 가 통째로 사장된다.

```
파이썬 : "치도리를 봤다"          ← 보고만 한다
Unity  : "치도리가 나가는지"      ← 호스트가 정한다
```

이 경계 덕분에 두 PC 의 상태가 어긋나는 것이 **구조적으로 불가능**하고,
파이썬이 죽어도 그 플레이어의 *입력*만 멎을 뿐 판은 멀쩡하다.

### D.2 순수 규칙 엔진

`BattleRules` 는 `UnityEngine` 도 `Unity.Netcode` 도 참조하지 않는 순수 C# 이다.
함수는 두 개뿐이고, 자기 상태를 갖지 않는다.

```csharp
CastResult      TryCast(BattleState s, int slot, int jutsuId, float now, IRandomSource rng);
List<ResolveResult> Tick(BattleState s, float now, IRandomSource rng);
```

`IRandomSource` 를 주입하는 이유는 분신술 주사위를 테스트에서 고정하기 위해서다.
주사위를 굴리는 쪽은 언제나 서버 한 곳뿐이라, 결과만 퍼뜨리면 화면이 어긋나지 않는다.

`.asmdef` 로 어셈블리를 갈라두면 **유니티가 이 순수성을 강제해준다** —
asmdef 어셈블리는 `Assembly-CSharp` 를 참조할 수 없으므로, 규칙 엔진에서
`PVPPlayerSync` 를 실수로 끌어다 쓰는 코드는 컴파일 자체가 되지 않는다.

### D.3 네트워크로 오가는 것

동기화하는 상태는 최소한으로 줄였다. 투사체를 `NetworkList` 로 복제하지 않고
**발사/도착 이벤트만** 보낸다 — 2인 대전이라 늦게 들어오는 관전자가 없으므로,
클라이언트는 이벤트만으로 비행을 그릴 수 있다.

| 방향 | 내용 |
|---|---|
| 클라 → 서버 | `CastJutsuRpc(jutsuId)` — 슬롯은 보내지 않는다 (사칭 방지, `SenderClientId` 로 판별) |
| 서버 → 전체 | `JutsuCastRpc` 발사 · `JutsuResolvedRpc` 도착 · `MatchOverRpc` 승패 |
| 서버 → 한 명 | `RecognitionRpc` 잠금 on/off · `CastRejectedRpc` 거절 사유 |
| 기존 재사용 | 체력·차크라는 `PVPPlayerSync` 의 NetworkVariable 에 그대로 흘려넣는다 |

마지막 줄이 핵심이다. 그 덕에 익환님 HUD 브리지와 규민님 HUD 프리팹이
**아무 수정 없이** 그대로 동작한다.

### D.4 파이썬 ↔ Unity 프로토콜

`run_tracker` 가 쓰는 5005/5008/5009 는 건드리지 않는다. 5009 를 같이 쓰면
`StateReceiver` 가 최신 패킷만 들고 있는 구조 때문에 전투 메시지가
`blend`/`clip` 을 덮어써 수인 애니메이션이 끊긴다.

```
uplink   5010   cast / sign / progress / heartbeat
downlink 5011   recognition / rejected / match
```

- **시전은 3번 보낸다.** UDP 하나가 사라지면 플레이어가 시퀀스를 만든 2.5~3.5초가
  통째로 날아간다. `seq` 를 붙여 Unity 가 중복을 지운다. 사인·하트비트는 연속적이라
  하나쯤 잃어도 보이지 않으므로 반복하지 않는다.
- **downlink 가 §3 의 인식 잠금을 '진짜'로 만든다.** Unity 에서 시전을 무시하는 것만으로는
  부족하다 — 파이썬의 시퀀스 버퍼가 계속 차면 잠금이 풀리는 순간 묵은 시퀀스가
  즉시 완성된다. 그래서 Unity 가 내려보내면 `SignSmoother` 와 시퀀스 버퍼를 리셋한다.
  덤으로 잠금 6초 동안 추론을 건너뛰어 GPU 가 쉰다.

### D.5 구현 중 확정한 것 (설계서에 없던 부분)

- **시전 시간(2.5s / 3.5s)은 게임이 강제하지 않는다.** 사인을 취하는 시간은 인식
  파이프라인에서 이미 흘러갔고, 시전 완료는 시퀀스가 인식된 순간 그 자체다.
  Unity 가 여기서 또 기다리면 기술 하나에 5초가 걸린다.
  `cast_seconds` 는 HUD 진행바 예측 전용 값으로 남긴다.
- **회피 지속이 도착 시각과 정확히 같으면 회피는 실패한다.** §4.3 이 지속시간으로
  "발사를 보고 나서 움직여라" 를 강제하는 것이 목적이므로, 동시 타이밍은 선제 시전한
  쪽이 손해를 보는 방향으로 끊었다.
- **인식 잠금은 타이머가 아니라 투사체의 존재로 표현한다.** "내가 날린 투사체가 아직
  있으면 잠김." 이렇게 두면 §4.4 의 잠금 소유권 이전이 필드 두 개를 맞바꾸는 것으로 끝난다.
